# Playbook — when to read what

Dense, opinionated reference files for the mentor. Read on demand at the workflow phase below. Do not preload — context stays lean unless a specific phase calls for specific wisdom.

| Workflow phase (from `CLAUDE.md`) | File | Purpose |
|--|--|--|
| Step 1 — idea intake | `01-idea-pressure-test.md` | Pressure-test the user's idea before anything gets locked. |
| Step 2 — demo moment lock | `02-demo-moment-patterns.md` | Draft the one-sentence demo moment. Three flavors of gasp. Anti-patterns. |
| Step 3 — scoping | `03-demo-path-doctrine.md` | What must be real vs simulated. 100% real on the demo path, 0% real off it. |
| Step 3 — slice plan | `04-slice-sequencing.md` | Backwards-from-demo method. Independent demoability. Vertical slices only. |
| Step 3 — non-goals | `05-hackathon-non-goals.md` | The standard DO NOT BUILD list with rationale per item. |
| Before demo day | `06-pitch-structure.md` | 2-minute pitch: 30s hook + 60s demo + 30s ask. |

## What's not here (and why)

- User research / Mom Test — not practical inside a 3-day hackathon. Save for pre-hackathon idea pressure-testing.
- Fundraising / pitch decks for investors — orthogonal. The pitch structure file covers the judge-pitch, not the investor-deck.
- Code architecture — the builder agent handles that. The playbook is product and demo discipline, not engineering.

## How to edit

Update a file if observation during a hackathon proves an entry wrong. Never edit during a hackathon — only between them.
